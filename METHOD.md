# Метод обучения

## 1. Цикл изучения одной темы

Каждая тема проходит пять шагов. Теория и практика разделены, но идут вместе: ориентир примерно **30% теории / 70% практики**.

| Шаг | Что делаешь ты | Что делаю я |
|---|---|---|
| 1. Теория | Читаешь источники и пишешь конспект **своими словами** (`theory.md`), отвечая на наводящие вопросы | Даю 5–8 наводящих вопросов и ссылки (официальная документация в приоритете, затем статьи и обсуждения) |
| 2. Проверка теории | Отвечаешь на контрольные вопросы в треде, без подсматривания | Проверяю, исправляю неверные термины и формулировки, даю ссылку, где это описано |
| 3. Практика | Выполняешь задание в отдельной ветке, открываешь Pull Request | Ставлю задание как GitHub Issue с критериями приёмки (Definition of Done) |
| 4. Проверка практики | Чинишь замечания, пока CI зелёный и ревью пройдено | Автопроверки в CI + code review в PR: указываю *где* проблема и *куда смотреть*, но не пишу исправление за тебя |
| 5. Защита и ретро | Объясняешь «почему так, а не иначе», пишешь короткую ретроспективу | Задаю 2–3 вопроса «а что если…», закрываю тему |

## 2. Как проверяется работа (4 уровня)

1. **Автоматически (CI в GitHub Actions)**: линтеры (`shellcheck` для Bash, `hadolint` для Dockerfile, `yamllint`, `markdownlint`), тесты, сборка. Красный CI = работа не принята.
2. **Code review**: я оставляю комментарии в PR как старший коллега. Подсказки, а не готовые ответы.
3. **Воспроизводимость**: по твоему README любой (и я в чистом контейнере) должен поднять результат с нуля. Если не поднимается, задание не закрыто.
4. **Устная защита**: вопросы «почему выбрал это решение», «что сломается, если…». Понимание важнее работающего кода.

Тема считается закрытой, когда пройдены все четыре уровня.

## 3. Структура репозитория

```
devops_roadmap/
├── README.md              # роадмап с чекбоксами по этапам и прогрессом
├── GLOSSARY.md            # словарь терминов (пополняешь сам, я проверяю)
├── stages/
│   └── 01-linux/
│       ├── theory.md      # конспект своими словами
│       ├── questions.md   # контрольные вопросы и твои ответы
│       ├── tasks/         # решения практических заданий
│       └── retro.md       # что было сложно, что понял
└── .github/workflows/     # CI, который проверяет твою работу
```

Задания живут в **GitHub Issues** (одна задача = один Issue), решения приходят через **Pull Request**, который закрывает Issue. Так ты с первого дня работаешь в том же процессе, что и в настоящей DevOps-команде.

## 4. Расписание (работа 9–17, 5/2)

Ориентир **8–9 часов в неделю**. Меньше, но регулярно, работает лучше, чем марафоны по выходным.

| День | Время | Что делаем |
|---|---|---|
| Пн | 1 ч | Теория: чтение по наводящим вопросам, конспект |
| Вт | 1 ч | Теория + контрольные вопросы в треде |
| Ср | 1 ч | Практика: начало задания из Issue |
| Чт | 1 ч | Практика: продолжение, открыть PR |
| Пт | отдых | |
| Сб | 3 ч | Большая практика: доделать задание, починить CI и замечания ревью |
| Вс | 1 ч | Защита («почему так»), ретро, повторение старых терминов из GLOSSARY.md |

Один этап занимает в среднем 2–4 недели. Если неделя выпала (работа, усталость), просто сдвигаем план, без «догонять».

## 5. Практика без бюджета

Всё, кроме облака, делаем локально и бесплатно:

| Что нужно | Чем заменяем аренду VDS |
|---|---|
| Серверы для Linux, Ansible, Nginx | Виртуальные машины на ПК с Windows (32 ГБ) или на ноутбуке с Fedora через KVM/libvirt; удобно управлять через Vagrant |
| Docker | Podman/Docker на Fedora |
| CI/CD | GitHub Actions (бесплатно для публичных репозиториев), деплой web-версии `dungeon_deck` на GitHub Pages |
| Terraform | Сначала локальные провайдеры (Docker, libvirt), чтобы освоить синтаксис и state |
| Kubernetes | kind, minikube или k3s в локальной VM |
| Мониторинг | Prometheus + Grafana в Docker Compose |
| Облако (этап 10) | Откладываем до конца; там используем стартовый грант для новых аккаунтов (условия проверим, когда дойдём) |

Этапы и прогресс: см. [README.md](README.md).
